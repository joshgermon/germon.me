# 17-11-26

## What I've learned going all in on Effect

A few months ago I was chatting with another engineer about result types. The idea is pretty simple: instead of a function that returns some data and might throw, it returns either the data or a typed error, and the caller has to handle both.

```ts
// Instead of this
function processMyData(data: Input): TransformedData;

// This
function processMyData(data: Input): Result<TransformedData, ProcessError>;
```

I'd been rewriting the same little `Result` helper in every project, so I was thinking it was probably time to just pick a library for it. Then I mentioned that what I actually love is [Effect](https://effect.website), but that it'd be a much harder sell. They ended up more excited about Effect than the helper. They quoted the tagline on its homepage back at me, "Reliable TypeScript for the AI era", and that was pretty much enough for them.

So I went all in on a side project to see how it actually holds up. It's a backend I've been working on that handles bookings, payments, forms and a small admin app, and it all runs on Cloudflare Workers, on Effect v4. Here's what stuck with me.

### The type tells you how it fails

This is the part that sold me. Here's the function that checks a Cloudflare Turnstile token when someone submits a form (trimmed a little):

```ts
export const verify = Effect.fn('Turnstile.verify')(function* (
  settings: Settings,
  visitor: Visitor,
): Effect.fn.Return<Accepted, Rejected | Unavailable, HttpClient.HttpClient> {
  const client = (yield* HttpClient.HttpClient).pipe(HttpClient.filterStatusOk);
  // ...build the siteverify request
  const reply = yield* client.execute(request).pipe(
    Effect.flatMap(HttpClientResponse.schemaBodyJson(Siteverify)),
    Effect.timeout(Duration.seconds(5)),
    Effect.catchTags({
      TimeoutError: () => new Unavailable({ reason: 'timeout' }),
      SchemaError: () => new Unavailable({ reason: 'bad_response' }),
      HttpClientError: () => new Unavailable({ reason: 'network' }),
    }),
  );
  // ...
});
```

The return type reads like a sentence. It gives back `Accepted`, it can fail as `Rejected` or `Unavailable`, and it needs an `HttpClient` to run. A timeout, a bad JSON body and a network error are three different failures underneath, but to the rest of my code they're one thing, "Turnstile didn't give us an answer", with a reason attached for the logs.

With `try/catch` none of that is in the signature. You find out how a function fails by reading all of it, or in production.

### The compiler does the review

The API handler for form submissions turns each domain error into an HTTP error:

```ts
submissions.accept(payload).pipe(
  Effect.catchTags({
    'Submissions.FormUnavailable': () => Effect.fail(new FormUnavailable()),
    'Submissions.VerificationRejected': ({ reason, hostname }) =>
      Effect.fail(new VerificationRejected({ reason, hostname })),
    'Submissions.Conflict': () => Effect.fail(new SubmissionConflict()),
    // ...
  }),
);
```

The API contract lists the errors each endpoint is allowed to return, so if I add a new failure to the domain and forget to map it, the handler doesn't compile.

The best example of this was in the admin app. Each operation declares the failures it can send back to the browser, but nothing forced its implementation to stay inside that list. Once I made the types enforce it, 158 pairs of operation and failure that could have reached a user as a nameless 500 became compile errors. 150 of them turned out to be impossible once the types were tighter, and the other 8 now fail with a named reason. I would never have found those by reading the code.

### Dependency injection without a framework

When I showed them some of the code, the dependency injection was what clicked first. You declare services once, and Layers say how to build them:

```ts
export const Services = (env: Env, keepAlive: KeepAlive) =>
  Layer.mergeAll(
    Slack.layer,
    Stories.layer.pipe(
      Layer.provide([Slack.layer, layerKv(env.INSTAGRAM), layerImages(env.IMAGES)]),
    ),
    Submissions.layer.pipe(
      Layer.provide([Slack.layer, Database(env.DB), BackgroundLayer(keepAlive)]),
    ),
  ).pipe(Layer.provideMerge(Platform(env)));
```

The Cloudflare bindings (D1, KV, Images) come in at the edge and the domain code never sees `env`. It asks for a `Database` and gets one, and in tests it gets an in-memory one.

One thing I'd tell myself earlier is don't make everything a service. My rule now is that something becomes a service only when it really varies in production or has a real owner, and wanting to swap a value in a test isn't enough. Otherwise the layer graph gets harder to read than the code it wires up.

### Do you have to go all in?

We went back and forth on this one for a while. The docs read to them like you have to be all in, with Effect right up to the top-level call. My take was that you don't. You can write modules that are fully Effect and call them from Next.js, Hono or TanStack Start like any other function, and I've done all three.

But also, yes, you should go all in where you can. The value comes from the edges being honest, and one stray `fetch`, `JSON.parse` or `new Date()` in the middle means the types are lying again. So the API Worker's lint bans `async`, `new Promise`, `JSON` and Node modules. Fetch goes through `HttpClient`, dates through `DateTime`, timers through `Effect.sleep` and JSON through `Schema`. The domain packages can't touch `Date`, `Math.random` or `fetch` at all.

### Where it hurt

It isn't free though. A few things that bit me:

- HttpApi is still marked unstable in v4, so `effect` is pinned to an exact version and every upgrade is a small project.
- Starting some I/O in a fiber while a layer was being built hung every request. That one took a while to find, and it's now a written rule.
- The Effect language service only reads the nearest `tsconfig.json`. My server config lived in a `tsconfig.server.json`, so its checks never ran. Moving it surfaced 32 findings I thought were already covered.
- `Effect.die('some message')` logged as "Unknown", which is the least useful thing a crash can say. I replaced those strings with a named `Broken` defect that says which invariant broke and for which ids.
- The learning curve is real. The first reaction I got when I showed it off was "this is literally RxJS". It kind of is, but RxJS was jank in practice and this isn't.

### Effect and agents

Most of this code was written with coding agents, and Effect suits them better than I expected. The types carry so much that a wrong change usually fails to compile instead of failing in production.

Two things made a difference. The first is that agents answer Effect v4 questions from memory, and their memory is mostly v3. The `effect` package ships its own `AGENTS.md`, so every package that uses Effect has a `CLAUDE.md` that imports it, and agents read the real API before they write any code.

The second is that agents copy the style of the nearest file, good or bad, so the rules live in lint instead of prose. I use the Effect rules from [anti-slop](https://github.com/dmmulroy/anti-slop) (no comparing `_tag` by hand), the Effect language service's own checks (`yield* new NotFound()` instead of `yield* Effect.fail(new NotFound())`) and a few rules of my own. Each rule has a test file that proves it fires, because I found two guards that had been silently doing nothing.

### If you want to try it

Start with Kit Langton's [effect.institute](https://www.effect.institute). It explains the why better than I can, and it's narrated, so you can pretty much listen to it like an audiobook. His [Visual Effect](https://effect.kitlangton.com) examples are good once you want to see how the pieces actually run. Then pick one part of an app with real failure modes, like a payment or a webhook, and write just that part in Effect.
