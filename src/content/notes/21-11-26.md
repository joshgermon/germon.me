# 21-11-26

## I built my own Windows client for Rex while I waited for the real one

I've been using [Rex](https://www.superlogical.com/rex) on my Mac for a while now. It's the terminal and multiplexer from Superlogical, Mitchell Hashimoto's company after HashiCorp, and it's built on libghostty like Ghostty is. My sessions live on a Linux box called dasher, so I can close the app, open it somewhere else and everything is still there, splits and all.

The problem is that my main machine is a Windows PC. There is an official Rex client for Windows, but it's in alpha and I didn't have access yet. I could have just waited, but I also wanted to see what a properly native Windows version would feel like (Mica, rounded corners, the real Windows controls), and I was curious how Rex actually works under the hood. So I built one while I waited, and called it Windex.

![Switching tabs, splitting and zooming panes, and moving between sessions on different servers](/notes/21-11-26/windex-tour.gif)

### What it does

It connects to Rex servers over SSH or HTTPS, and it finds the machines on my tailnet so I don't have to type addresses. Tabs, splits, zoom and sessions all come from the server, so if I split a pane on Windows it's split on my Mac too.

It also has the things I use every day: find in scrollback, a command palette, a session switcher, and a little "Needs input" badge when Codex or Claude Code is waiting on me. You can drag files onto a pane to upload them, and Rex types the uploaded path at the prompt, which is really handy when you want to hand an agent a screenshot.

![Dropping two files on a pane uploads them to the server and types their paths at the prompt](/notes/21-11-26/windex-upload.gif)

### How Rex talks

There isn't a public spec for the protocol, so a lot of this was reading [rex-rune](https://github.com/shuv1337/rex-rune), an open source Linux client, poking at a throwaway server and writing down what I found.

It's all WebSockets. There's a control channel at `/api/control` that speaks JSON (`rex.control.v1`). That's where the client says hello, gets the sessions and the layout of every tab, and asks for things like a new split (trimmed a little):

```json
{
  "type": "request",
  "id": "12",
  "method": "session.new_split",
  "payload": {
    "session_id": "session:…",
    "anchor_id": "block:…",
    "direction": "horizontal",
    "side": "after",
    "focus": true
  }
}
```

Then every pane gets its own data channel at `/api/data` (`rex.data.terminal.v1`). The first thing down that channel is a Ghostty snapshot of the terminal (it literally starts with the bytes `GHOSTSNP`), and after that it's just the raw output from the shell. Because the snapshot comes straight out of libghostty, a pane opened on Windows looks exactly like it does on the server, scrollback and all.

Over SSH there's no port to connect to, because the server listens on a unix socket. So Windex runs `ssh -L` to forward a local port to that socket and connects through it. With Tailscale SSH there aren't even any keys to set up.

### Two halves

The app is split in two. A Rust library (`rexcore.dll`) owns everything protocol and terminal shaped: the connections, the model of sessions and tabs, and a libghostty-vt terminal for each pane, each on its own thread. The Windows app is C# and WinUI 3, and it owns everything pixel and input shaped. They talk through a small C API. Commands go in as JSON, a model of hosts, sessions, tabs and panes comes back out, and each pane hands over its grid of cells for the app to draw with Win2D, without copying it.

![Windex.exe talks to rexcore.dll through a C API, and the core reaches the Rex server over an SSH forward or a direct WebSocket](/notes/21-11-26/windex-architecture.svg)

Leaning on libghostty meant I didn't have to write any of the actually hard parts of a terminal. Mitchell has since shipped [libghostty 1.0](https://mitchellh.com/writing/libghostty-1-0) with a stable C API, which should make this kind of thing even easier.

### Making it feel like Windows

This was the fun part. The window uses Mica and the panes are rounded glass cards like on the Mac, but everything around them is the real Windows stuff. Settings are the standard Windows settings cards, uploads and downloads use the normal file pickers, you can drag files in from Explorer, progress from the terminal shows up on the taskbar button, and when something needs me there's a badge on the taskbar and a Windows notification. Shortcuts follow Windows Terminal rather than the Mac, so `Ctrl+Shift+D` splits right and `Alt+Shift+-` splits down.

### Where it bit me

- **Ownership.** In Rex, the client that owns a pane decides its size. The first version claimed whatever session it showed when it started, which meant just opening Windex would have resized the session I had open on my Mac. Now it only claims a session once I actually open it.
- **A shortcut that did nothing.** Split down on `Ctrl+Shift+E` just didn't work. It turned out another app on my PC had registered it as a global hotkey, so Windows never passed it on. Windex now checks each shortcut when you open the settings and tells you which ones are taken.
- **Testing on a PC I was using.** The UI tests send real key presses, and early on one of them may have sent a few to my Chrome window instead. Now anything that needs the keyboard waits until I've been away for a minute, and won't type at all if the app isn't in front.
- **PowerShell.** Variables in PowerShell aren't case sensitive, so `$h` (the window handle) and `$H` (the height) are the same variable. That made every recording for the README 2,180 pixels tall until I worked out why.

### How I built it

Most of the code was written with coding agents. I described what I wanted, pointed them at rex-rune and some screenshots of Rex on my Mac, and ran it as a few tracks in parallel (the Rust core, the terminal renderer and the Windows shell), each with a separate reviewer checking the work. Then there was a second round for file transfer, find and the visual polish, which compared screenshots against the Mac version until it looked right.

My job was mostly steering, testing against my own server, and saying "no, more like the Mac". The agents also needed some guard rails to test a desktop app on a machine I was actually using: throwaway test sessions on the server that they had to clean up afterwards, my real sessions were off limits, and the keyboard rule above.

### Should you use it?

Honestly, if you can get access, use the official Rex for Windows. It's the real thing and it's going to get way more love than this. Windex is unofficial, it's built against one version of the protocol, and a Rex update could break it. There's no installer either, so you have to build it yourself.

But if you want to poke around, see how the protocol works or add your own features, it's all on GitHub at [github.com/joshgermon/windex](https://github.com/joshgermon/windex). The README has the diagrams and a list of what it can't do yet.
